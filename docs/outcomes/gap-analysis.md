# Gap analysis

!!! note "Draft"
    Section 5 holds draft outcomes and proposals, for further consideration, and only what test results support. The rows below come from the local runs, from the three dress rehearsals on Rahti, with the hub and both sites in one cluster, from the probes at the DE, FI and CZ Nodes, and from the run over the FI and CZ Nodes on 2026-11-24 ([Report](report.md)). Whatever is added here stays a draft: it gets finalized elsewhere.

How far federated learning with NVFlare works through WES and TES today, and what separates it from the [Design](../background/design.md). It may work today with caveats or workarounds. Shared work on standards, implementations, and setup, configuration and implementation guidance is the way to the end state.

This page only gets filled from results. For what this testbed takes shortcuts on in the first place, see [Shortcuts and hacks](../testbed/shortcuts.md): a row here names a shortcut where a test showed what it costs.

| Gap | Type | Evidence (test) | Workaround today | What the workaround costs | Proposal | Path to the design |
|---|---|---|---|---|---|---|
| <span id="g1">**G1**</span> A TES task can't ask for an address, a name or a port that others reach, so the FL server can't be a task like the clients | Standard | [T5](../tests/t5-server-task.md), local, 2026-11-04 and 2026-11-11: passes only on a Funnel hacked to give its executors a fixed name on the networks of all sites ([H6](../testbed/shortcuts.md#h6)) | The FL server runs beside the WES, at the hub, with a public FL port and a fixed name ([B1](../testbed/options.md#b1-server-beside-the-wes), [H1](../testbed/shortcuts.md#h1)); clients only dial out ([T3](../tests/t3-isolation.md)) | The hub is a long-running service outside TES, with a public port that someone has to run, secure and monitor. Its port and name are fixed, so there's one run at a time ([G12](#g12)) | [Service-like tasks](proposals.md#service-like-tasks) | [Scheduling participants](../background/design.md#scheduling-participants) |
| <span id="g2">**G2**</span> A TES task can't state how long it may run | Standard | Every local run of [T2](../tests/t2-wes-to-tes.md), 2026-11-04 and 2026-11-11, and both dress rehearsals of [T8](../tests/t8-real-sites.md) on Rahti, 2026-11-12 and 2026-11-16, ran with the wrapper below; [H14](../testbed/shortcuts.md#h14) | A `timeout` of 30 minutes around each client, in the image, and constants in the WES | No backend enforces it, and a site can't see it before it admits a task. Without the wrapper, a client that loses the server retries forever and holds its slot at the site | [Time limits for tasks](proposals.md#time-limits-for-tasks) | [Scheduling participants](../background/design.md#scheduling-participants) |
| <span id="g3">**G3**</span> TES has no way to hand a secret to a task that keeps it out of task records and logs | Standard | [T2](../tests/t2-wes-to-tes.md), local, 2026-11-11, which checks since [#30](https://github.com/elixir-cloud-aai/nvflare-wes-testbed/pull/30) that no kit is among the inputs of a task; [H3](../testbed/shortcuts.md#h3) | Each site makes its own key in its task, and sends a signing request over a one-time link in the command of its executor. The WES deletes the link once it's used, and at the end of the run ([H4](../testbed/shortcuts.md#h4)) | Whoever reads task records or logs at a TES or a gateway while a run lasts, before the task of a site uses the link, can get a certificate of that site for the run. No private key travels any more | [Secrets for tasks](proposals.md#secrets-for-tasks) | [Identity and credentials](../background/design.md#identity-and-credentials) |
| <span id="g4">**G4**</span> A task is pinned to a site by the URL of a TES, not by a property of the site or of its data | Standard, implementation | [T4](../tests/t4-protes.md), local, 2026-11-04 (10/10 checks) and 2026-11-11 (12/12); [H11](../testbed/shortcuts.md#h11) | A static map of sites in the WES; through proTES, the tag `gateway.backends` with the URL of a TES, or proTES's identifier of it (the site's `backend`), which only moves the map into proTES | A run is tied to addresses: when a site moves its TES, every sites file changes. Nothing says which sites hold which data | [Pinning tasks by a property of a site](proposals.md#pinning-tasks-by-a-property-of-a-site) | [Scheduling participants](../background/design.md#scheduling-participants) |
| <span id="g5">**G5**</span> The WES needs a token for the TES of each site, which expires within hours, and nothing says where it gets one that every site accepts | Guidance | `tests/tokens_test.py`, against a mock provider only, in CI since 2026-11-12 ([#35](https://github.com/elixir-cloud-aai/nvflare-wes-testbed/issues/35)). All three dress rehearsals of T8 on Rahti, 2026-11-12 to 2026-11-19, used a TESK without authentication; on 2026-11-19, the hub sent a static LS Login access token for each site, which that TESK ignored. At the DE Node, 2026-11-21, two TES deployments accepted such a token for a probe task. On 2026-11-24, run `ae7742f2` over the FI and CZ Nodes: both TESKs checked one LS Login access token of one user, which the hub sent from its sites file ([Report](report.md#first-multi-site-run)) | Per site, a static token, a token file that the hub reads again before each request, or a refresh token or client credentials of an OAuth 2.0 provider ([Tokens for the TES of the sites](../setup/real-sites.md#tokens-for-the-tes-of-the-sites)) | The hub holds a token of one user, and acts as that user at every site; every site sees the same identity. Renewal not tried against a real provider, and not set up on Rahti: an access token lives about an hour, so one run per token, renewed by hand with a new sites file and a restart of the hub | – | [Identity and credentials](../background/design.md#identity-and-credentials) |
| <span id="g6">**G6**</span> The WES trusts one OIDC issuer, for one client, and every caller gets the same role in FLARE | Implementation | [T9](../tests/t9-auth.md), local, 2026-11-11, in CI; [#43](https://github.com/elixir-cloud-aai/nvflare-wes-testbed/pull/43), also tried with a token of an institutional Keycloak realm; [H5](../testbed/shortcuts.md#h5), [H22](../testbed/shortcuts.md#h22) | A mandatory bearer token from one trusted issuer, and an optional static list of allowed subjects. FLARE's admin for a run is the caller's email, or a name from its `sub` if the token has none (LS Login access tokens don't), always with the role `lead` | No groups, studies or roles: anyone the issuer vouches for may run jobs, unless the list names subjects. Another issuer takes a redeploy. No rate limiting ([H23](../testbed/shortcuts.md#h23)) | – | [Identity and credentials](../background/design.md#identity-and-credentials) |
| <span id="g7">**G7**</span> Rahti's admission refuses pods that ask for the seccomp profile `RuntimeDefault` | Guidance | Install of the chart on Rahti, 2026-11-12 ([What differed on Rahti](../setup/real-sites.md#what-differed-on-rahti)); [#32](https://github.com/elixir-cloud-aai/nvflare-wes-testbed/issues/32) | `podSecurityContext.seccompProfile=null` in the values of the chart | The chart can't ask for a seccomp profile there: which one applies is up to the cluster. Other OpenShift clusters may refuse the chart's default in the same way | – | – |
| <span id="g8">**G8**</span> Rahti's LimitRange allows a CPU limit of at most 5 times the request | Guidance | Install of the chart on Rahti, 2026-11-12: no pod was created ([#37](https://github.com/elixir-cloud-aai/nvflare-wes-testbed/issues/37)) | A default request of 400m for a limit of 2 CPUs ([#38](https://github.com/elixir-cloud-aai/nvflare-wes-testbed/pull/38)); `tests/chart.sh` checks the ratio in CI | More CPU reserved than an idle hub needs | – | – |
| <span id="g9">**G9**</span> NVFlare's FL server starts without its port if another process holds it, and only logs that | FL framework | [T8](../tests/t8-real-sites.md) on Rahti, 2026-11-12: a probe listener left in the hub's pod held the FL port, no site joined, and the run ended `SYSTEM_ERROR` after the start timeout ([#40](https://github.com/elixir-cloud-aai/nvflare-wes-testbed/issues/40)) | The WES checks that the port is free before a run, and looks for gRPC's bind failure in the server's log once it's up. A run then fails at once, and names the port ([#41](https://github.com/elixir-cloud-aai/nvflare-wes-testbed/pull/41)) | The check reads NVFlare's log, which may change with any release | – | – |
| <span id="g10">**G10**</span> The FL server only listens during a run, as each run's server has a CA of its own: without something else on the FL port between runs, a node can't probe an idle hub | Implementation | T8 on Rahti, 2026-11-16, before the workaround: the FL port was closed before the run, and open while it ran ([#46](https://github.com/elixir-cloud-aai/nvflare-wes-testbed/issues/46)) | Between runs, the WES answers probes on the FL port itself ([#47](https://github.com/elixir-cloud-aai/nvflare-wes-testbed/pull/47), on Rahti since 2026-11-17; `tests/probe_responder_test.py` in CI) | A public port that accepts and closes any connection while the hub is idle. With the responder off, probes need a listener at an agreed time | – | – |
| <span id="g11">**G11**</span> Rahti exposes the FL port only on a port between 30000 and 35000, through a `LoadBalancer` Service | Guidance | Install on Rahti, 2026-11-12: the FL port is 30002 ([What differed on Rahti](../setup/real-sites.md#what-differed-on-rahti), [#25](https://github.com/elixir-cloud-aai/nvflare-wes-testbed/issues/25)) | None needed in the same cluster. Whether other nodes let tasks out on such a port is what the probes ask ([#3](https://github.com/elixir-cloud-aai/nvflare-wes-testbed/issues/3)): at the DE Node, 2026-11-21, a task got out on neither 30002 nor 443; at the FI and CZ Nodes, 2026-11-24, tasks got out on 30002, and the run over both ended `COMPLETE` | A port that the firewalls of nodes may block more often than 443. [T7](../tests/t7-port-443.md)'s port 443 isn't in that range, so it would need a hub elsewhere, such as on a VM | – | – |
| <span id="g12">**G12**</span> The WES runs one run at a time, and keeps all state in memory | Implementation | [T2](../tests/t2-wes-to-tes.md), local; on Rahti, 2026-11-12 to 2026-11-17, each upgrade of the hub restarted its pod, which forgot its runs; [H2](../testbed/shortcuts.md#h2) | None | One caller can keep everyone else out by resubmitting as each run ends, and there's no cancel. An upgrade or a restart loses the records of all runs | – | – |
| <span id="g13">**G13**</span> TESK's filer and executors share a task's volume: on storage that only one node attaches at a time (`ReadWriteOnce`), an executor scheduled on another node than its filer can't start | Implementation | [T8](../tests/t8-real-sites.md) at the FI Node, 2026-11-24, run `1eae12bf`: `SYSTEM_ERROR`, as site 1's executor got `Multi-Attach`, then OpenStack's `400` "already attached", for its Cinder volume ([Report](report.md#of-the-sites)) | None: run again. In run `ae7742f2`, the same night, site 1's task at the same TESK got through | Any run at a TESK on such storage may fail, depending on where the scheduler puts its pods | – | – |
| <span id="g14">**G14**</span> TESK's task volumes on root-owned CSI storage, such as CephFS, aren't writable by tasks that don't run as root | Guidance | TESK at the CZ Node, under Pod Security `restricted`, 2026-11-23 and 2026-11-24, before the probe and run of [T8](../tests/t8-real-sites.md) ([generic-issues#122](https://github.com/elixir-cloud-aai/generic-issues/issues/122)) | `fsGroup` 100 on the filer and executor pods, in the TESK deployment | One more setting per cluster that an operator has to know; documented for TESK since ([TESK#341](https://github.com/elixir-cloud-aai/TESK/issues/341)) | – | – |

- **Type:** standard, implementation, FL framework or guidance.
